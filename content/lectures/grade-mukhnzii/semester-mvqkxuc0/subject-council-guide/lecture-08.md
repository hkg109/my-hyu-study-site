## 1. 전체 MVP 앞에 “작은 실습 서비스”를 둔다

기획서 v0.7의 MVP에는 실시간 공동편집과 기수 전환까지 들어 있다. 코딩 경험이 없는 팀이 처음부터 모든 기능을 동시에 만들면 화면·DB·권한 문제를 구분하기 어렵다. 먼저 다음 한 줄을 끝까지 완성한다.

> [!EXAM]
> ==blue:학교 계정 로그인 → 승인된 구성원 확인 → Task 등록 → 목록·상세 조회 → 완료 처리 → 비허용 계정 거부 → Preview 배포==

이 실습은 최종 제품을 대신하지 않는다. 최종 기능을 만들 때 반복해서 필요한 흐름을 익히는 작은 연습이다. ==red:이 단계에서는 실제 학생회 개인정보 대신 가짜 계정과 가짜 업무를 쓴다.==

### 아홉 단계 학습 경로

[![준비, 화면 연습, 실제 저장, 계정·권한, 행사 묶음, 회의록 기본, 공동편집 PoC, 건의·기수, 운영 QA의 아홉 단계를 순서대로 놓고 단계마다 손에 남을 결과를 적은 경로. 공동편집 PoC가 가장 큰 기술 위험으로 강조되어 있다.](/materials/diagrams/cpg-08-learning-path.svg)](/materials/diagrams/cpg-08-learning-path.svg)

*그림 8-1 · 아홉 단계 학습 경로 — 누르면 원본 크기로 열린다.*

| 단계 | 배우고 만드는 것 | 손에 남아야 할 결과 | 다음으로 넘어가는 기준 |
| --- | --- | --- | --- |
| 준비 | 웹 구조, 요구사항 분해, GitHub | README, 첫 Issue·PR, 업무 흐름 그림 | 팀 전원이 PR을 만들고 리뷰받음 |
| 화면 연습 | HTML·CSS·JS·TS·React | 가짜 Task 목록·폼, 로딩·빈 목록·오류 화면 | 모바일과 키보드로 주요 흐름 확인 |
| 실제 저장 | Next.js·SQL·Supabase | Task 생성·조회·상태 변경 | 새로고침 후에도 자료가 남음 |
| 계정·권한 | Google 로그인, Allowlist, Membership, RLS | 계정별 내부 접근 차이 | 일반 학생·다른 Term 계정 거부 |
| 행사 묶음 | Event, ACL, Resource, Schedule, Handover | 행사 페이지의 연결된 자료 | Event 밖 사용자의 하위 접근 차단 |
| 회의록 기본 | Meeting ACL, BlockNote, Template, 상태 | 단일 사용자 저장과 다시 열기 | 열람자·편집자·CONFIRMED 구분 |
| 공동편집 PoC | Yjs, RPC, Realtime, Snapshot | 두 사용자 동시 편집 | 실패·중복·재접속에서도 복구 |
| 건의·기수 | 익명 건의, Term 전환, Archive Grant | 작성자 신원 분리와 읽기 전용 보관 | 담당자 API에 신원 없음, Grant 범위 확인 |
| 운영 QA | E2E, 접근성, 백업·복구, 로그 | 배포 점검표와 운영 매뉴얼 | 다른 팀원이 문서로 점검·복구 재현 |

이 표는 **기간을 약속하는 일정표가 아니다.** 팀의 수업·시험·학습 속도에 맞춰 조정한다. 특히 공동편집, 권한 회수, 복구 검증에는 별도 시간을 남긴다.

### 기획서 Phase 0~10과 연결

| 기획서 Phase | 준비할 지식 | 먼저 확인할 기술 위험 |
| --- | --- | --- |
| 0 설계 | 1, 3, 4, 5편 | ERD, 권한 상속, RLS 사례, BlockNote 기능·라이선스, `realtime.send()` PoC, 요금제 |
| 1 기반 | 2, 3, 5편 | Google Auth Hook 차단, 로컬·Preview 환경, DB 테스트 CI |
| 2~5 조직·업무·행사 | 3, 4, 6편 | 같은 Term 제약, Task ACL, Event 범위 축소 충돌, Storage 권한 |
| 6~7 회의록·CRDT | 5, 7편 | 초기 Snapshot, 저장 후 Broadcast, 순번, 재접속, 권한 회수 |
| 8~9 건의·기록 | 4, 7편 | 작성자 신원 분리, Term 전환, Archive Grant, Activity Log |
| 10 QA | 5편과 아래 점검표 | E2E, 동시 편집 실패 복구, DB·Storage 복원 |

> [!CAUTION]
> **Phase 0에서 정할 운영값:** 실시간 권한 회수 최대 지연, Update 묶음 간격, 파일 크기·형식 한도, 보존 기간, 요금제, 건의 이월 정책, 건의 빈도 제한. 정하지 않은 값은 `TBD`로 남기지 말고 Issue로 기록해 담당자를 붙인다.

## 2. 팀 역할과 협업 리듬

다섯 명이라면 다음처럼 나눌 수 있다. 인원이 적으면 겸임하되, ==red:권한 정책의 검토자는 작성자와 다른 사람==으로 둔다.

| 역할 | 책임 | 첫 학습 산출물 |
| --- | --- | --- |
| 기획·진행 | 요구사항, 우선순위, Issue, 완료 기준 | Task 생성 작업 카드와 테스트 표 |
| 화면 | 폼, 목록, 모바일, 접근성 | 가짜 Task 목록과 상태별 화면 |
| 앱 연결 | Next.js 서버 처리, Supabase 연결, 오류 | 실제 Task 저장과 다시 읽기 |
| 데이터·권한 | ERD, 마이그레이션, Auth, RLS | 활성 Membership과 허용·거부 DB 테스트 |
| 품질·운영 | Preview, E2E, 로그, 백업, 운영 문서 | 배포 전 점검표와 복구 실습 |

### 한 주의 기본 흐름

1. 회의에서 이번 주의 작은 Issue와 완료 기준을 정한다.
2. 담당자가 Branch에서 구현하고 자기 계정으로 먼저 확인한다.
3. Pull Request에 변경 이유, 바뀐 화면·DB·권한, 허용·거부 결과를 적는다.
4. 리뷰어가 코드를 읽고 Preview에서 직접 실행한다.
5. 수정 후 Merge하고, 완료 기준의 증거를 Issue에 남긴다.
6. 막힌 문제는 “누가, 어디서, 무엇을 했고, 무엇이 보였는지” 적어 다음 회의 전에 공유한다.

Branch를 오래 방치하지 않는다. DB 마이그레이션, Auth, RLS, 실시간 권한처럼 경계가 큰 변경은 화면 변경과 **별도 PR**로 나누면 검토하기 쉽다.

## 3. AI 코딩 도구를 쓸 때

AI에게 전체 서비스를 한 번에 만들라고 하면 기획서의 권한·Term·상태 규칙을 **추측**하게 된다. 다음을 함께 준다.

==blue:한 가지 목표 · 현재 구조 · 입력·출력 · 권한 조건 · 바꾸지 말아야 할 범위 · 검증 방법==

> [!EXAMPLE]
> **좋은 요청 예시**
>
> 현재 Next.js App Router와 TypeScript 프로젝트의 업무 생성 폼에서 제목 필수 검증을 추가해 줘. 빈 제목은 서버에서 거부하고 입력창 아래에 한국어 오류를 보여 줘. 기존 tasks 테이블과 RLS 정책은 변경하지 말아 줘. 정상 제목과 빈 제목을 각각 어떻게 검증했는지 알려 줘.

**변경을 받은 뒤**

1. 파일 차이(diff)를 읽는다.
2. TypeScript 검사와 빌드를 실행한다.
3. 브라우저에서 정상·오류 입력을 시험한다.
4. 권한이 바뀌었다면 허용·거부 계정으로 직접 확인한다.
5. 패키지 이름과 함수가 현재 버전에 실제로 있는지 공식 문서와 맞춘다.

오류를 전달할 때는 “안 돼요” 대신 ==실행한 명령, 오류 메시지, 관련 파일, 기대 결과, 실제 결과, 재현 순서==를 적는다.

> [!CAUTION]
> 비밀 키와 실제 학생 개인정보·건의 원문은 AI 요청에 붙여 넣지 않는다. 같은 오류를 가짜 데이터로 재현해서 보낸다.

## 4. 바로 복사해 쓰는 작업 양식

### 기능 Issue

```text
제목:
사용자와 목표:
입력값과 필수 항목:
성공했을 때 화면과 DB의 변화:
실패·오류 상황:
조회/생성/수정 권한:
같은 Term·Event 상위 범위 검사:
허용 계정의 기대 결과:
거부 계정의 기대 결과:
이번 작업에서 제외할 것:
```

### 버그 보고

```text
환경: 로컬 / Preview / Production
브라우저와 계정 Role:
재현 순서:
1.
2.
3.
기대 결과:
실제 결과:
오류 메시지/화면: (개인정보와 비밀값 제거)
다시 발생하는지:
```

### Pull Request 설명

```text
연결된 Issue:
변경 목적:
변경 파일과 데이터 구조:
권한 또는 개인정보에 미치는 영향:
직접 실행한 정상 사례:
직접 실행한 거부·오류 사례:
빌드/테스트 결과:
Preview 주소 또는 화면:
남은 제약:
```

| 자원 | 계정·조건 | 행동 | 기대 | 실제 | 통과 |
| --- | --- | --- | --- | --- | --- |
| RESTRICTED Event | Event ACL에 없는 국원 | 상세 URL 열기 | 거부 |  |  |
| Event 하위 Task | Task ACL에는 있으나 Event 접근 없음 | 목록·상세 조회 | 거부 |  |  |
| Meeting | 열람자, 편집자 아님 | CRDT Update 저장 | 거부 |  |  |
| Suggestion | 배정된 국원 | 작성자 신원 API 호출 | 거부 |  |  |

## 5. 배포 전 최종 확인

기획서 v0.7 14절에는 세부 완료 기준 **38개**가 있다. 아래는 이를 학습 관점에서 묶은 것이다. 실제 배포 판단은 기획서 14절을 항목별로 확인한다.

### 기능과 권한

- [ ] 학교 외 계정은 Auth Hook에서 거부되며 `auth.users`·`profiles`에 행이 생기지 않는다.
- [ ] 승인된 계정만 내부 Membership이 생긴다.
- [ ] Role·Permission은 고정 규칙을 따르고 Position 이름으로 권한을 얻지 않는다.
- [ ] Task DEFAULT/RESTRICTED와 Event ALL_COUNCIL/RESTRICTED가 예상대로 작동한다.
- [ ] Event 밖 사용자는 하위 Task·Meeting의 담당자·편집자·ACL 대상이 될 수 없다(UI와 RPC 모두).
- [ ] Event 범위 축소 시 충돌을 보여 주고 해결한 뒤 저장한다.
- [ ] Task 변경 가능 필드와 상태 전이를 서버에서 검사하고, 삭제 대신 보관·복원 이력을 남긴다.
- [ ] Storage 객체, Dashboard, 하위 Activity Log도 상위 권한을 따른다.

### 회의록과 실시간 저장

- [ ] 기본 열람과 복수 국 Preset, 대표 작성자, 복수 편집자가 구분된다.
- [ ] 두 사용자가 새 회의록을 열어도 Template은 한 번만 들어간다.
- [ ] 저장된 Update만 Broadcast되고 클라이언트의 임의 CRDT Broadcast는 거부된다.
- [ ] 저장 실패·중복·Broadcast 유실·재접속·동시 Snapshot에서 내용이 복구된다.
- [ ] CONFIRMED 회의록은 편집자도 저장할 수 없다.
- [ ] DB 권한 회수는 즉시 적용되고 Realtime 수신 지연은 정한 한도 안에 있다.

### 건의·기수·운영

- [ ] 처리 담당자의 API·로그·검색·알림에 건의 작성자 신원이 없다.
- [ ] 작성자 공개 답변과 내부 메모가 분리되고 작성자는 내부 메모를 읽지 못한다.
- [ ] Term 전환, 미처리 건의 이월/마감, Membership 종료 책임 이관이 정한 정책대로 작동한다.
- [ ] CLOSED Term은 읽기 전용이고 유효한 Archive Grant 범위에서만 과거 자료를 읽는다.
- [ ] Activity Log에 민감 본문·신원·토큰·Signed URL이 없다.
- [ ] 시간 일정과 종일 일정이 구분되고 `Asia/Seoul` 표시가 맞다.
- [ ] 운영값의 TBD를 해소하고 DB와 Storage 복구를 실제로 한 번 시험했다.
- [ ] 허용·거부 RLS 사례가 DB 테스트로 자동 실행된다.
- [ ] 키보드·모바일·브라우저 호환성과 주요 화면의 로딩·오류 상태를 확인했다.
