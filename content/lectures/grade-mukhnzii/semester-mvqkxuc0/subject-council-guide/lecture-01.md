1부는 코드를 쓰기 전에 **서비스 전체 그림**을 잡는 부분이다. 사용자, 기능, 요청이 흐르는 길, 기획서를 작업으로 바꾸는 법을 차례로 본다.

## 1. 누구를 위한 서비스인가

이 플랫폼은 학생회 내부의 업무와 기록을 한곳에서 관리하는 웹 서비스다. 회장단은 조직과 권한을 관리하고, 국장은 자기 국 업무와 구성원을 관리하며, 국원은 배정받은 업무와 허용된 자료를 쓴다. 검증된 학교 계정으로 로그인한 일반 학생은 내부 운영 자료에 접근하지 않고 건의사항을 제출한다.

[![학교 외 계정은 Auth Hook에서 거부되고, 학교 계정 로그인 사용자는 일반 학생이며, 그 안에서 승인 명단과 현재 Term Membership이 있는 사람만 MEMBER, DIRECTOR, EXECUTIVE로 내부 자료를 쓰는 포함 관계 그림](/materials/diagrams/cpg-01a-user-scope.svg)](/materials/diagrams/cpg-01a-user-scope.svg)

*그림 1-1 · 로그인 ≠ 학생회 권한 — 누르면 원본 크기로 열린다.*

| 사용자 | 대표 행동 | 기본 경계 |
| --- | --- | --- |
| 일반 학생 | 건의 작성, 본인 건의 상태·공개 답변 확인 | 학생회 내부 업무·행사·회의록은 열람 불가 |
| 국원 (MEMBER) | 담당 업무 처리, 접근 가능한 행사 자료 열람, 지정된 회의록 편집 | 타 부서의 비허용 자료와 권한 설정은 접근 불가 |
| 국장 (DIRECTOR) | 자기 국 구성원·업무·행사 관리, 회의록 생성 | 다른 국 관리와 회장단 승격은 불가 |
| 회장단 (EXECUTIVE) | 조직 설정, 전체 운영 권한, 건의 작성자 신원 확인 | 실제 개인정보 접근은 목적과 기록을 남겨 관리 |

서비스 메뉴는 **Dashboard, 업무, 행사, 회의록, 건의사항, 관리**로 묶인다. 행사는 업무·일정·자료·회의록·인수인계의 상위 묶음이다. 모든 내부 기록은 어느 학생회 **기수**(Term)에 속하는지 알아야 한다.

> [!NOTE]
> **그림 읽는 법:** 바깥에서 안으로 들어갈수록 볼 수 있는 자료가 많아진다. 가장 바깥 점선(학교 외 계정)은 서비스 사용자조차 되지 못한다. 회색 칸(일반 학생)에서 진한 칸(학생회 구성원)으로 들어가는 조건은 ==로그인이 아니라 승인 명단과 현재 Term Membership==이다.

## 2. 웹 서비스의 세 부분과 요청 흐름

웹 서비스의 기본 구조는 ==blue:브라우저 화면 → 서버 처리 → 데이터베이스==다.

- **프론트엔드:** 사용자가 보는 목록, 입력창, 버튼, 오류 안내를 만든다.
- **백엔드:** 사용자가 보낸 요청과 로그인 상태를 확인하고 처리한다.
- **데이터베이스:** 업무·행사·구성원 같은 기록을 보관하고 권한 정책을 적용한다.

국장이 업무를 등록하면 다음 일이 일어난다.

[![국장이 업무를 입력하면 브라우저가 형식을 확인하고, 서버와 DB가 로그인·현재 Term·생성 권한·담당자 지정 가능 여부를 확인한 뒤 tasks 테이블에 저장하고 화면이 결과를 다시 읽는 흐름. 형식 오류는 입력창 아래 안내로, 권한 거부는 거부 이유 안내로 빠진다.](/materials/diagrams/cpg-01b-request-flow.svg)](/materials/diagrams/cpg-01b-request-flow.svg)

*그림 1-2 · 업무 하나가 저장되는 길 — 누르면 원본 크기로 열린다.*

> [!CAUTION]
> ==red:화면에 보이는 결과와 실제 저장은 다르다.== 저장 버튼을 누른 직후 화면에 새 업무가 나타나도 DB 저장에 실패했다면 새로고침 후 사라질 수 있다. 반대로 DB에는 저장됐지만 목록을 다시 불러오지 않아 화면에 안 보일 수도 있다. 문제를 찾을 때는 **입력 → 요청 → 권한 검사 → DB 저장 → 결과 표시**를 차례로 확인한다.

### API와 RPC

- **API**는 프로그램끼리 요청과 결과를 주고받는 약속된 통로다.
- **RPC**는 서버나 DB에 정의한 함수를 **이름으로** 호출하는 방식이다.

기획서의 `save_meeting_update()`는 회의록 변경을 저장하는 DB 함수다. 사용자는 CRDT Update 테이블에 직접 쓰지 못하고, 이 함수가 권한과 상태를 확인한 뒤 저장한다(5편).

### 직접 해보기

종이에 **사용자·브라우저·Next.js·Supabase** 네 칸을 그리고 “업무 저장” 요청을 화살표로 잇는다. 제목이 비었을 때, 로그인하지 않았을 때, DB 연결이 실패했을 때 각각 **어느 칸에서** 어떤 안내를 줄지 적는다.

> [!QUIZ]
> 버튼을 숨기는 것과 DB가 접근을 거부하는 것은 왜 다른가?

> [!ANSWER]
> 버튼 숨김은 브라우저 화면의 **편의**일 뿐이다. 사용자는 상세 URL을 직접 입력하거나 개발자 도구로 같은 요청을 보낼 수 있다. DB(RLS·RPC)의 거부는 요청이 어떤 경로로 오든 **실제로 막는 보안**이다. 그래서 권한 테스트는 버튼뿐 아니라 URL 직접 접근·API 요청까지 확인한다.

## 3. 기획서 문장을 개발 작업으로 바꾸기

“업무 관리 기능을 만든다”는 문장은 너무 크다. 업무 생성, 목록, 상세, 수정, 상태 변경, 완료 후 재개, 공개 범위 설정, 보관·복원으로 나눈다. 그리고 각각 다섯 가지를 적는다.

| 항목 | “업무 생성” 예시 |
| --- | --- |
| 사용자 | 현재 Term의 활성 DIRECTOR 또는 EXECUTIVE |
| 입력 | 제목, 설명, 담당 국·담당자, 마감일, 공개 모드 |
| 성공 | 업무 ID가 만들어지고 상세 화면에서 새 기록을 확인 |
| 실패 | 제목 누락, 잘못된 날짜, 권한 없음, 연결 실패를 구분 |
| 권한·검증 | 생성 권한, 같은 Term 대상, Event 소속이면 Event 열람 범위 확인 |

기능 하나를 **화면·데이터·권한·테스트** 네 칸으로 다시 나누면 해야 할 작업이 보인다.

| 칸 | 적을 질문 |
| --- | --- |
| 화면 | 사용자가 무엇을 입력하고, 로딩·빈 목록·오류를 어떻게 보나? |
| 데이터 | 어떤 테이블과 필드에 저장되나? 다른 기록과 어떻게 연결되나? |
| 권한 | 누가 조회·생성·수정·보관할 수 있나? 주소를 직접 입력해도 같은가? |
| 테스트 | 허용 사례와 거부 사례를 어떤 계정으로 확인하나? |

> [!EXAMPLE]
> 완료 기준은 “정상 작동”처럼 모호하게 쓰지 않는다.
>
> - ✗ 업무 생성이 잘 된다.
> - ✓ ==현재 Term 국장 A는 자기 국 업무를 만들 수 있고, 일반 학생 B와 다른 Term의 국장 C가 보낸 같은 저장 요청은 거부된다.==
>
> 다른 사람이 **관찰해서 확인할 수 있는 결과**로 적는다.
