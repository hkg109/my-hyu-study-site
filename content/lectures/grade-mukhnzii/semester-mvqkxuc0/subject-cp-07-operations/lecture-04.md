## 1. 무엇을 남기나

| 문서 | 위치 | 독자 | 내용 |
| --- | --- | --- | --- |
| README | `README.md` | 처음 온 모든 사람 | 무엇인지, 실행 방법, 문서 지도 |
| 설정 기록 | `docs/setup.md` | 개발 담당 | 대시보드 설정 위치와 순서 (07-1 6절). 비밀 값 없음 |
| 결정 기록 | `docs/decisions/NNNN-제목.md` | 미래의 개발자 | 왜 이렇게 정했나 |
| 운영 문서 | `docs/handover-checklist.md`, `docs/emergency/` | 회장단·개발 담당 | 점검표(07-3), 비상 절차(06-5) |
| 기획서 | `docs/spec/` 또는 이 강의 00 과목 링크 | 모두 | 무엇을 만드는가 |

## 2. README의 뼈대

```markdown
# 정보시스템학과 학생회 운영 플랫폼

학생회 구성원이 업무·행사·회의록·건의를 관리하고 다음 기수에 기록을 남기는 서비스.

## 빠른 시작 (개발)
1. Node 22, Git 설치
2. `git clone https://github.com/<학생회-org>/council-platform`
3. `cp .env.example .env.local` → 개발 담당에게 **개발용** Supabase URL·공개 키를 받아 채움
4. `npm install` → `npm run dev` → http://localhost:3000
5. 테스트 계정은 `supabase/seed.sql` 참고 (가짜 데이터)

## 문서 지도
- 무엇을 만드나: 학습 가이드 00 과목 / docs/spec
- 처음 공부할 것: 학습 가이드 01 → 02–05 → 06
- 왜 이렇게 만들었나: docs/decisions
- 운영·기수 교대: docs/handover-checklist.md

## 규칙 (요약)
- main 직접 push 금지, PR + 리뷰 1명 + CI 통과
- 비밀 값·실제 개인정보 커밋 금지 (공개 저장소)
- DB 변경은 마이그레이션 파일로만, RLS 변경은 db-reviewers 승인
```

README는 **짧게** 유지하고 자세한 내용은 링크로 보냅니다. 길어지면 아무도 끝까지 읽지 않습니다.

## 3. 결정 기록 (ADR)

"왜 Hobby를 쓰지?", "왜 회의록 저장에 Vercel을 안 거치지?" 같은 질문에 답하는 짧은 문서입니다. 결정할 때마다 하나씩, 번호를 붙여 씁니다.

```markdown
<!-- docs/decisions/0003-council-handover-two-person.md -->
# 0003. 회장단 권한 이양은 두 사람 승인으로

- 날짜: 2026-10-28
- 상태: 확정

## 배경
기획서 v0.7은 매 기수 첫 EXECUTIVE를 운영자 SQL로 등록하게 했다. 매년 개발자가 DB를 직접 고쳐야 한다.

## 결정
현 회장단이 화면에서 다음 회장단을 지정하고, 요청자가 아닌 다른 회장단이 승인한다.
운영자 절차는 첫 기수와 회장단 공백 시에만 쓴다.

## 결과
- 좋아진 점: 개발자 없이 기수 교대 가능, 기록이 한 곳(activity_logs)에 남음
- 감수한 점: 회장단이 1명뿐이면 화면으로 불가 → 비상 절차 필요
```

| 언제 ADR을 쓰나 | 예 |
| --- | --- |
| 되돌리기 어려운 선택 | 요금제, 저장 구조, 인증 방식 |
| 기획서와 다르게 갈 때 | 이 강의 00-4의 추가 결정 네 개 |
| 같은 질문이 두 번 나왔을 때 | "왜 이건 RLS가 아니라 함수로 써요?" |

이미 정한 결정을 바꿀 때는 기존 문서를 지우지 않고, 새 ADR에 "0003을 대체함"이라고 적습니다. 이력이 남아야 같은 고민을 반복하지 않습니다.

## 4. 테스트도 문서다

04-5편의 RLS 테스트를 다시 보면:

```sql
select is(…, 0, '재무국원은 지정되지 않은 RESTRICTED 업무를 못 본다');
```

이 한 줄은 **기획서 4.2절을 실행 가능한 문장으로** 옮긴 것입니다. 문서는 낡아도 아무도 모르지만, 테스트는 규칙이 깨지면 CI가 빨갛게 알려 줍니다. 그래서:

- 테스트 설명은 **한국어 문장**으로, 기획서 표현을 그대로 씁니다.
- 새 권한 규칙을 만들면 허용·거부 테스트를 먼저 씁니다.
- 기획서 완료 기준 번호를 테스트 파일 주석에 적어 두면, 어떤 기준이 자동으로 검증되는지 한눈에 보입니다.

*그림 07-4 · 아홉 단계 학습 경로 — 누르면 원본 크기로 열린다.*

이미 서비스가 돌아가는 상태에서 들어온 개발자라면:

| 주 | 읽을 것 | 할 것 |
| --- | --- | --- |
| 1주 | 00 과목, 01 과목 | README대로 개발 환경 실행, 가짜 계정으로 모든 화면 둘러보기 |
| 2주 | 02·03 과목 | 작은 화면 Issue 하나(문구·접근성 수정)로 **첫 PR** |
| 3주 | 04 과목 | `supabase/tests`를 읽고, 기존 규칙에 거부 테스트 하나 추가하는 PR |
| 4주 | 06 과목에서 맡을 기능 편 | 그 기능의 Issue를 맡음 |
| 필요할 때 | 05 과목 | 회의록을 맡을 때만 |
| 기수 교대 전 | 07 과목 | 점검표를 직접 한 번 수행 |

처음부터 서비스를 만드는 기수라면 그림의 아홉 단계를 따릅니다. 각 단계는 기간 약속이 아니라 **다음 단계로 넘어갈 기준**입니다. 가장 큰 기술 위험인 공동편집은 7단계에서 PoC로 따로 검증합니다(기획서 Phase 0·7).

## 6. 이 강의도 남기는 문서다

이 학습 가이드(00–07 과목)는 기획서 v0.7과 그 이후 결정을 기준으로 썼습니다. 기획서나 결정이 바뀌면:

1. 저장소의 ADR을 먼저 씁니다.
2. 이 가이드의 해당 편(특히 00-4 추가 결정사항)을 함께 고칩니다.
3. 예제 코드가 실제 코드와 달라졌다면 실제 코드 쪽 링크를 남깁니다.

> [!QUIZ]
> 2029 기수 개발자가 "Vercel Pro로 바꾸자"고 제안했습니다. 결정하기 전에 무엇을 읽고, 결정 후 무엇을 남겨야 하나요?

> [!ANSWER]
> 읽을 것: Hobby를 고른 이유가 적힌 ADR(07-1의 결정, 00-4 결정 1)과 현재 사용량. 남길 것: 새 ADR("0001을 대체함")에 배경·결정·비용·바뀌는 배포 방식을 적고, `docs/setup.md`와 07-1·07-2편의 해당 부분을 고칩니다. 공용 계정의 결제 수단과 담당자도 점검표에 추가합니다.

> [!QUIZ]
> 새 개발자의 첫 PR로 "회의록 공동편집 개선"보다 "업무 목록의 버튼 label 수정"이 더 좋은 이유는?

> [!ANSWER]
> 첫 PR의 목적은 기능이 아니라 **흐름을 한 번 끝까지 겪는 것**(브랜치 → 커밋 → PR → CI → 리뷰 → Merge → 자동 배포)입니다. 작고 위험이 낮은 변경이어야 리뷰가 빠르고, 실패해도 서비스에 영향이 없습니다. 공동편집은 05 과목과 PoC 경험이 쌓인 뒤 맡습니다.
