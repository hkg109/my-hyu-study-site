## 1. 웹 서비스의 등장인물 셋

학생회 플랫폼에서 "내 업무 목록"을 여는 장면을 생각해 봅시다. 세 등장인물이 있습니다.

| 등장인물 | 비유 | 하는 일 | 이 프로젝트에서 |
| --- | --- | --- | --- |
| **브라우저** | 손님 | 주소를 열고, 받은 화면을 그리고, 클릭·입력을 받는다 | Chrome, Safari |
| **서버** | 주방 | 요청을 받아 무엇을 보여 줄지 계산하고 응답을 만든다 | Vercel에서 도는 Next.js |
| **데이터베이스(DB)** | 창고 | 데이터를 오래 보관하고, 꺼내고, 바꾼다 | Supabase의 PostgreSQL |

> [!NOTE]
> "프론트엔드"는 브라우저 쪽 코드, "백엔드"는 서버 쪽 코드를 말합니다. DB는 백엔드가 쓰는 저장소입니다. 01-5편에서 셋의 역할을 다시 정리합니다.

## 2. URL 읽기

```text
https://council.example.com/tasks?status=TODO#top
└─┬──┘   └───────┬────────┘└─┬──┘└────┬────┘└┬┘
프로토콜       도메인          경로     쿼리    조각
```

| 부분 | 뜻 | 예 |
| --- | --- | --- |
| 프로토콜 | 어떤 규칙으로 통신할지. `https`는 암호화된 HTTP | `https` |
| 도메인 | 어느 서버로 갈지 | `council.example.com` |
| 경로 | 그 서버 안의 어느 페이지인지 | `/tasks` |
| 쿼리 | 페이지에 넘기는 추가 조건. `?` 뒤에 `이름=값`, 여러 개면 `&`로 연결 | `status=TODO` |
| 조각 | 페이지 안의 위치. 서버로는 보내지 않음 | `#top` |

Next.js에서는 **경로가 곧 폴더 구조**입니다. `/tasks`는 `app/tasks/page.tsx` 파일이 담당합니다(02-2편).

> [!CAUTION]
> 쿼리는 주소창·방문 기록·서버 로그에 그대로 남습니다. 이메일이나 학번 같은 개인정보를 쿼리에 넣지 않습니다.

## 3. HTTP 요청과 응답

브라우저와 서버는 **HTTP**라는 규칙으로 대화합니다. 대화는 항상 "요청 하나 → 응답 하나"입니다.

[![브라우저가 GET 요청에 주소와 쿠키를 담아 보내면 Next.js 서버가 코드를 실행하고 상태 코드와 HTML을 담은 응답을 돌려주고 브라우저가 화면을 그리는 순서](/materials/diagrams/cpg-10-http.svg)](/materials/diagrams/cpg-10-http.svg)

*그림 01-1 · 주소를 열면 생기는 일 — 누르면 원본 크기로 열린다.*

### 요청(Request)의 구성

```http
GET /tasks?status=TODO HTTP/1.1
Host: council.example.com
Cookie: sb-access-token=eyJhbGciOi...
Accept: text/html
```

| 줄 | 뜻 |
| --- | --- |
| `GET /tasks?status=TODO` | **메서드**와 경로. GET은 "읽어 오기" |
| `Host:` | 어느 사이트에 보내는지 |
| `Cookie:` | 브라우저가 저장해 둔 값. 로그인 상태가 여기 들어 있음 |
| `Accept:` | 어떤 형식의 응답을 원하는지 |

### 메서드

| 메서드 | 뜻 | 학생회 예 |
| --- | --- | --- |
| GET | 읽기 | 업무 목록 보기 |
| POST | 새로 만들기·실행하기 | 업무 등록, 건의 제출 |
| PATCH / PUT | 고치기 | 업무 상태 변경 |
| DELETE | 지우기 | (이 프로젝트는 대부분 보관 처리로 대신함) |

### 응답(Response)의 구성

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Set-Cookie: sb-access-token=...; HttpOnly; Secure

<!doctype html>
<html> ... 업무 목록 ... </html>
```

첫 줄의 숫자가 **상태 코드**입니다. 오류를 찾을 때 가장 먼저 보는 값입니다.

| 코드 | 뜻 | 이 프로젝트에서 보게 되는 때 |
| --- | --- | --- |
| 200 | 성공 | 정상 |
| 201 | 새로 만들어짐 | 업무 등록 성공 |
| 302 / 307 | 다른 주소로 가라 | 로그인 안 한 사람을 `/login`으로 보낼 때 |
| 400 | 요청 형식이 잘못됨 | 제목 없이 업무 저장 |
| 401 | 로그인이 필요함 | 세션이 만료됨 |
| 403 | 로그인은 했지만 권한 없음 | 국원이 다른 국 제한 업무를 열 때 |
| 404 | 없음 | 지워졌거나 잘못된 주소 |
| 409 | 충돌 | 두 사람이 인수인계를 동시에 고쳤을 때 |
| 500 | 서버 오류 | 코드 버그 |

> [!EXAM]
> **401과 403의 차이:** 401은 "누구인지 모름(인증 안 됨)", 403은 "누구인지 알지만 이건 안 됨(인가 안 됨)". 03-3편 로그인과 04-4편 권한에서 계속 나옵니다.

## 4. JSON — 데이터를 주고받는 글자 형식

화면(HTML) 대신 **데이터만** 주고받을 때는 JSON을 씁니다. Supabase가 돌려주는 결과도 JSON입니다.

```json
{
  "id": "6f1c2a90-1b2e-4c7d-9a1e-2d3f4b5c6d7e",
  "title": "축제 부스 배치도 만들기",
  "status": "IN_PROGRESS",
  "assignee_id": null,
  "tags": ["축제", "홍보"],
  "due_date": "2026-11-20"
}
```

| 읽는 법 | 예 |
| --- | --- |
| `{ }` 안은 **객체**: `"이름": 값` 쌍의 묶음 | 업무 하나 |
| `[ ]` 안은 **배열**: 값의 순서 있는 목록 | `["축제", "홍보"]` |
| 글자는 큰따옴표 `" "` | `"IN_PROGRESS"` |
| 숫자·참거짓·없음은 따옴표 없이 | `3`, `true`, `null` |
| 날짜는 정해진 형식의 글자 | `"2026-11-20"` |

`null`은 "값이 없음"입니다. 위 예에서 `assignee_id`가 `null`이면 아직 담당자가 없다는 뜻입니다.

## 5. 쿠키와 로그인 상태

HTTP는 요청 하나하나가 서로를 기억하지 못합니다. 그래서 "이 사람은 로그인했다"는 사실을 **쿠키**로 기억합니다.

1. Google 로그인에 성공하면 서버가 응답에 `Set-Cookie`로 **세션 토큰**을 넣습니다.
2. 브라우저는 이 쿠키를 저장해 두고, 같은 사이트에 보내는 **모든 요청**에 `Cookie:`로 붙입니다.
3. 서버는 쿠키 속 토큰을 확인해 "이 요청은 누구의 것인지" 압니다.

이 프로젝트에서 그 토큰이 **JWT**(서명이 붙은 디지털 출입증)입니다. JWT는 "누구인지"만 알려 줄 뿐, "무엇을 볼 수 있는지"는 매 요청마다 DB가 다시 판단합니다(04-4편).

| 쿠키 옵션 | 뜻 |
| --- | --- |
| `HttpOnly` | JavaScript가 읽을 수 없음 → 악성 스크립트가 토큰을 훔치기 어려움 |
| `Secure` | https에서만 전송 |
| `SameSite` | 다른 사이트에서 시작된 요청에 쿠키를 붙일지 |

## 6. 개발자 도구로 직접 보기

브라우저에서 `F12`(Mac은 `Cmd+Option+I`)를 누르면 개발자 도구가 열립니다.

| 탭 | 볼 수 있는 것 |
| --- | --- |
| **Elements** | 지금 화면의 HTML 구조 |
| **Console** | JavaScript 오류와 `console.log` 출력 |
| **Network** | 모든 요청·응답, 상태 코드, 주고받은 JSON |
| **Application** | 저장된 쿠키, localStorage |

> [!CAUTION]
> Network 탭은 **사용자도 볼 수 있습니다.** 그래서 건의 담당자에게 보내는 응답 JSON에 작성자 ID가 섞여 있으면, 화면에 안 보여도 유출입니다. 기획서가 "API·네트워크 탭·로그 어디에도"라고 강조하는 이유입니다.

### 직접 해보기

1. 아무 사이트나 열고 Network 탭을 켠 뒤 새로고침합니다.
2. 첫 번째 요청을 눌러 메서드·상태 코드·`Cookie` 헤더를 찾습니다.
3. `Fetch/XHR` 필터를 눌러 JSON으로 오가는 요청을 하나 열고, Response 탭에서 객체와 배열을 구분해 봅니다.

> [!QUIZ]
> 로그인한 국원이 `/tasks/123`을 열었는데, 그 업무가 다른 국의 RESTRICTED 업무입니다. 서버가 돌려줄 가장 알맞은 상태 코드는 무엇이고, 왜 401이 아닌가요?

> [!ANSWER]
> **403**(또는 존재 자체를 숨기려면 404)입니다. 쿠키로 누구인지는 확인됐으니 인증 문제(401)가 아니라, 그 자료를 볼 권한이 없는 인가 문제입니다. 실제로는 RLS가 행을 아예 돌려주지 않으므로 "찾을 수 없음"으로 보여 주는 경우가 많습니다.

> [!QUIZ]
> 아래 JSON에서 담당자가 정해졌는지, 태그가 몇 개인지 답하세요.
> `{"title":"간식 행사","assignee_id":"a1b2","tags":["복지"],"done":false}`

> [!ANSWER]
> `assignee_id`에 값 `"a1b2"`가 있으니 담당자가 정해졌습니다. `tags`는 배열 `["복지"]`라서 태그는 1개입니다. `done`은 `false`이므로 아직 끝나지 않았습니다.

> [!NOTE]
> 01편을 읽다 보면 "언어", "라이브러리", "프레임워크", "패키지", "API", "서비스" 같은 말이 계속 나옵니다. 헷갈리면 [01-5 2절 · 도구를 부르는 말 구분하기](/lectures/grade-mukhnzii/semester-mvqkxuc0/subject-cp-01-web/lecture-05)를 먼저 보세요. 한 표에 정리되어 있습니다. 짧게 말하면 **언어**는 코드를 쓰는 문법, **라이브러리**는 내 코드가 불러 쓰는 기능 묶음, **프레임워크**는 내 코드를 불러 주는 뼈대, **서비스**는 계정을 만들어 쓰는 남의 서버입니다.
